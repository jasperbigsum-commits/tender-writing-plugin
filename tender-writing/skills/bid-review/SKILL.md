# 投标文件自查与导出

读取 [检查规则](../bid-writing/references/review-rules.md)、[契约](../bid-writing/references/data-contract.md) 及全部本次适用资料。既有投标文件先以 `bid` 用途导入；模型需实际完整研读并建立要求、响应、章节和证据关联，`ingest` 本身不会执行语义审查。

1. 用 `audit` 做结构与基础检查，逐项查看来源而不是只看计数。输出每个问题的招标依据、投标位置、风险、缺口、建议修改和核验方法。脚本 `blocker` 表示交付前尚有事项，不等于已构成法定废标。
2. 独立做语义核验：拆解每个复合要求，比较真实响应，核对证书主体/有效期、技术指标、服务承诺、金额与日期。自动矩阵覆盖只证明已关联，不能证明实质满足。
3. 实际查看制式附件、签章位置、暗标身份线索、元数据和电子签章要求。图像不可见或无文字不能直接判定附件或印章缺失。电子证书/CA有效性与线下动作不得声称由纯文本验证完成。
4. 对照招标格式渲染最终文件并检查所有页面，包含图表、跨页、标题、目录、页码、空白页、附件顺序和页边距。当前脚本提供基础 A4 排版，复杂模板用宿主文档工具保真处理。
5. 相似检查说明语料范围和方法。脚本只给出同一项目正文之间的字符串相似线索；不把它说成跨供应商查重、改图识别或串标认定。受控模板/招标公共表述与独创段落分开核验。
6. 已实际完成的专项复核用 `review` 记录类型、检查人、范围、发现、依据。模型做的检查如实写 assistant；用户的检查只在其确实提供结果时记录其身份。签章或跨文件查重不适用时说明原因；semantic/format 不能标不适用。禁止为了通过导出而编造复核。

修改源文件、要求、证据、目录、正文或主数据后，旧专项复核按指纹自动失效。先完成修改再重新核验。`submission` 只会检查台账和复核状态；导出后的 Word 仍需渲染核对，不声称“导出即保证合规”。

默认交付 `draft` 与清晰缺口。对已完成实际专项复核的项目，可生成 `submission` 版本及哈希回执。最终列出文件绝对路径、检查范围、未解决项和提交前行动。
